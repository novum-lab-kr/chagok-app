# 운영 로그와 앱 오류 수집 계획

출시 뒤에는 운영에서 서버 테스트를 돌리지 않는다([개발 설정](../../DEV-SETUP.md) 「운영 서버 함수 올리기」, 2026-10-26 결정). 운영에서 생기는 문제는 서버 로그와 앱 오류 보고로 찾는다. 이 계획은 두 부분이다.

- **A. 서버 로그:** 운영 서버의 로그가 남고, 서버 쪽 오류가 생기면 메일로 안다.
- **B. 앱 오류와 강제 종료:** 사용자의 기기에서 난 오류와 강제 종료를 안다.

B는 개인정보 수집이 새로 생겨 처리방침과 스토어 신고가 바뀐다. 출시 전까지는 약관과 처리방침 변경을 모두 1판에 넣으므로(AGENTS.md 「출시 전까지」), B는 출시 전에 정하고 넣어야 한다.

## A. 서버 로그

### 지금 상태 (2026-10-26 서버에서 읽음)

| 무엇 | 지금 | 문제 |
| --- | --- | --- |
| 보관 위치 | 컨테이너 11개 모두 Docker 기본 `json-file`. 크기 제한 설정 없음(`~/.config/docker/daemon.json` 없음) | 컨테이너를 다시 만들면 그 컨테이너의 로그가 사라진다. 오늘 다시 만든 auth와 functions는 오늘 것만 있다 |
| 크기 | pooler 12MB, realtime 1.9MB(5일). 대부분 상태 확인 요청 | 제한이 없어 계속 커진다. 디스크는 59%라 당장은 괜찮다 |
| 게이트웨이(envoy) | 요청마다 한 줄(평균 119바이트): 경로, 상태 코드, 크기, User-Agent. 보내는 쪽 주소는 모두 `172.18.0.1` | 실제 사용자 IP가 남지 않는다. Caddy에는 접속 기록 설정이 없다 |
| auth | JSON 줄(평균 188바이트). 요청마다 `path`, `status`, `request_id`, `duration`. 오류는 `level=error` | 로그는 충분하다. 보관만 문제 |
| 함수 | 실패 때 `console.error`로 단계와 원문 오류(`delete-account: apple revoke failed ...`). 그 밖에 정상 종료 안내(`early termination`)가 섞인다 | 실패를 찾을 수는 있지만 따로 모으지 않는다 |
| PostgREST | 24시간 0줄. 5xx가 생길 때만 남는 설정으로 보인다 | 확인 못 함 |
| DB | `log_min_messages=fatal`. 오류(ERROR)는 남지 않는다 | RPC 안에서 난 오류는 서버에 흔적이 없다. 앱이 받은 오류 응답뿐이다 |
| 별도 로그 서비스 | Supabase의 analytics(Logflare, Vector)는 띄우지 않았다 | 메모리가 커서 일부러 뺐다 |
| 알림 | Healthchecks.io 6개(API, 컨테이너, 디스크, 메모리, 백업, R2 용량) | 서버가 살아 있어도 요청이 계속 실패하는 경우는 알 수 없다 |

**양:** 최근 24시간, 감시용 상태 확인 줄을 빼면 게이트웨이, auth, 함수, storage를 합쳐 약 330줄, 100KB다(대부분 그날 돌린 서버 테스트). 출시 뒤 하루 사용자 1,000명이 30번씩 요청한다고 치면 하루 약 10MB, 90일 약 900MB로 어림한다(추정). 디스크 여유는 80GB다.

### 정한 것 (2026-10-26 사용자 확정: A1 1안, A2 90일, A3 남기지 않음)

**A1. 로그를 어디에 모을까**

| | 방법 | 좋은 점 | 아쉬운 점 |
| --- | --- | --- | --- |
| **1안 (추천)** | 서버 안에 직접 모은다. 5분마다 스크립트가 주요 컨테이너의 새 로그를 `~/logs/`의 날짜별 파일에 덧붙이고, 지난 날짜 파일은 압축하고, 오래된 파일은 지운다 | 바깥으로 보내지 않아 처리방침과 스토어 신고가 그대로다. 메모리를 거의 안 쓴다. 지금 감시 스크립트와 같은 방식이다 | 찾을 때 `grep`으로 본다. 화면은 없다 |
| 2안 | Supabase analytics(Logflare, Vector)를 켠다 | Studio 화면에서 검색한다 | 메모리를 1GB 안팎 더 쓴다. 지금 메모리 경고 기준(1.5GB 남음)에 자주 걸릴 수 있다 |
| 3안 | 바깥 로그 서비스(Better Stack, Grafana Cloud 무료)로 보낸다 | 화면, 검색, 알림이 다 있다 | 처리방침의 수탁자와 국외 이전, 스토어 개인정보 신고를 바꿔야 한다 |

5분은 가져오는 간격이다. 쌓이는 양은 요청 수로 정해지고, 같은 줄은 한 번만 저장된다. 간격이 짧으면 오류 알림이 빨리 오고, 컨테이너가 예기치 않게 다시 만들어질 때 잃는 양이 적다.

**A2. 며칠 남길까** — **90일.**
- 통신비밀보호법 시행령 41조 2항 2호는 전기통신사업자의 접속 로그 보관 기간을 3개월 이상으로 정한다(2026-10-26 원문 확인). 노붐랩이 여기에 해당하는지는 확인하지 않았다. 90일이면 어느 쪽이든 맞는다.
- 처리방침의 보관 기간 문구는 정책 저장소에서 확인하고 맞춘다. 지금 [스토어 개인정보 신고 초안](../../release-store-privacy-draft.md)에는 "서버 접속 기록에 IP 주소가 며칠 남을 수 있다"고만 적혀 있다.

**A3. 실제 사용자 IP를 남길까** — **남기지 않는다(지금처럼).**
- 오류를 찾는 데는 필요 없다. 남기면 개인정보가 되어 보관과 파기를 처리방침에 적어야 한다.
- 누군가 서버를 두드릴 때 막을 근거가 필요해지면, 그때 Caddy 접속 기록을 켜는 것을 정한다.

### 1안의 순서

모두 `ssh chagok@187.127.114.161`에서 한다. 서버를 바꾸는 단계는 할 때마다 명령을 보여 주고 허락받는다.

1. **로그 모으기 스크립트** `~/logs/collect.sh`(700)와 5분 타이머 `chagok-logs.timer`.
   - 대상: auth, functions, envoy, storage, rest, db. pooler와 realtime은 상태 확인 요청뿐이라 모으지 않는다.
   - 컨테이너마다 지난번 읽은 시각부터 지금까지(`docker logs --since --until`)를 `~/logs/<서비스>/<날짜>.log`(600)에 덧붙인다.
   - 감시 스크립트가 5분마다 부르는 상태 확인 줄(envoy의 `/auth/v1/health`)은 뺀다.
   - 지난 날짜 파일은 `gzip`으로 압축하고, 90일 넘은 파일은 지운다.
2. **다시 만들기 전에 모으기.** `sh run.sh recreate`나 업데이트 전에 `collect.sh`를 한 번 돌린다. DEV-SETUP의 함수 올리기와 업데이트 순서에 한 줄씩 더한다.
3. **Docker 로그 크기 제한.** `docker-compose.chagok.yml`에서 모든 서비스에 `max-size: 10m`, `max-file: 3`.
   - 적용하려면 컨테이너 11개를 모두 다시 만들어야 한다. 로그인과 백업이 1분쯤 끊긴다.
   - 출시 전이라 지금 하는 것이 낫다.
4. **DB 오류 남기기.** `log_min_messages=error`, `log_min_error_statement=panic`.
   - 오류 내용은 남기되, 오류 난 SQL 문장은 남기지 않는다. 문장에는 기록 내용 같은 사용자 데이터가 들어갈 수 있다.
   - `ALTER SYSTEM`으로 바꾸면 DB 데이터 폴더에 저장되고, 다시 시작하지 않아도 적용된다.
5. **서버 오류 알림.** Healthchecks.io에 7번째 점검 「서버 오류」를 만든다(무료 20개 안).
   - `collect.sh`가 이번 5분에 모은 줄에서 오류를 센다.
     - auth `level=error`
     - 함수 `console.error` 줄
     - envoy 5xx
     - storage `level>=50`
     - rest 줄 전부
     - db `ERROR`
   - 오류가 있으면 `/fail`을 보낸다. 본문에는 서비스별 개수와 메시지 앞부분만 넣는다(예: `functions 1 (delete-account: kakao unlink failed)`). 사용자 ID, 이메일, 토큰은 넣지 않는다.
   - 메일은 상태가 바뀔 때만 온다. 실패가 이어지는 동안 다시 오지 않고, 오류 없는 5분이 오면 「다시 정상」이 온다.
6. **확인.**
   - 토큰 없이 함수를 불러 401 줄이 모이는지
   - 404는 5xx가 아니라 알림이 안 오는지
   - 테스트용 `RAISE`로 DB 오류를 내 「서버 오류」가 빨갛게 되는지
   - 사용자에게 메일이 왔는지 봐 달라고 한다.
7. **기록.** DEV-SETUP에 「운영 서버 로그」 절을 쓴다. 어디에 있고, 어떻게 찾고(`grep request_id`), 며칠 남는지. 운영 서버 계획 6단계에 7번째 점검을 더한다.

## B. 앱 오류와 강제 종료

### 지금 상태

- 앱에는 화면을 그리다 난 예외를 받는 `ErrorBoundary`(`app/_layout.tsx:65`)만 있다. 안내 화면을 보여 줄 뿐 어디에도 보내지 않는다.
- 화면 밖에서 난 예외(동기화, 위젯 동기화, 구매 연결 등)와 네이티브 강제 종료는 아무도 모른다.
- 스토어 신고 초안: "진단(충돌 기록), 사용 데이터: 지금은 수집하는 SDK가 없다." 로그인하지 않은 사용자는 "기록이 기기 밖으로 나가지 않으므로 수집이 아니다."
- 이미 들어간 바깥 SDK: 카카오, Google 로그인, AdMob(`react-native-google-mobile-ads`), RevenueCat.

### 스토어 기준 (2026-10-26 원문 확인)

[Apple App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/):
- 기기 밖으로 보내 요청 처리보다 오래 남기면 「수집」이다. 분석이나 광고가 아니어도 신고한다. 충돌 기록은 「진단 › 충돌 데이터」다.
- 신고하지 않아도 되는 예외는 조건을 모두 맞춰야 하는데, 자동으로 보내는 충돌 기록은 맞지 않는다(사용자가 매번 직접 고르는 경우만 해당).
- 사용자 ID나 기기 ID를 붙이면 「사용자와 연결됨」이다. 보내기 전에 식별자를 빼면 「연결되지 않음」으로 신고할 수 있다.
- "You are not responsible for disclosing data collected by Apple." Apple이 모으는 충돌 보고(아래 B0)는 우리가 신고하지 않는다. 다만 이 문장이 Xcode Organizer의 충돌 보고를 직접 가리키지는 않는다. 넣기 전에 App Store Connect 도움말로 한 번 더 확인한다.

### B0. 기본으로 깔고 가는 것 (비용 없음, 코드 없음)

- **iOS:** App Store Connect와 Xcode Organizer의 충돌 보고. TestFlight 충돌 보고와 피드백. 기기 설정에서 「앱 개발자와 공유」를 켠 사용자의 것만 온다.
- **Android:** Google Play Console의 Android vitals(비정상 종료, ANR).
- 한계: 공유를 켠 사용자만 오고, 하루 이상 늦게 오고, 앱 코드(JavaScript)의 오류 내용은 거의 알 수 없다.
- 할 일: 출시 체크리스트에 「주 1회 Organizer와 Android vitals 보기」를 더한다.

### B1. 무엇으로 모을까 — **Sentry** (2026-10-26 사용자 확정, 아래 1안)

| | 방법 | 좋은 점 | 아쉬운 점 |
| --- | --- | --- | --- |
| **1안 (추천)** | **Sentry** (`@sentry/react-native`, Expo 공식 안내 있음) | 네이티브 강제 종료와 JavaScript 오류를 모두 받는다. EAS Build가 소스맵을 자동으로 올려 오류 위치를 원래 코드 줄로 본다. 오류마다 메일 알림, 화면, 검색이 있다. 무료(한 달 오류 5,000개, 30일 보관, 사용자 1명) | 바깥 회사로 보낸다. 처리방침에 수탁자와 국외 이전(미국 또는 EU)을 더하고, 스토어 신고를 바꾼다. 의존성을 더할 때 `react-dom` 고정과 충돌하는지, Expo 57과 RN 0.86에서 되는지 시험해야 한다 |
| 2안 | **우리 서버로 직접 보내기.** 앱의 전역 오류 처리기와 `ErrorBoundary`가 오류를 기기에 모았다가 운영 서버의 `app_errors` 표로 보낸다. 네이티브 강제 종료는 B0에 맡긴다 | 바깥 회사가 없어 국외 이전이 늘지 않는다. A의 서버 로그와 같은 곳에서 본다 | 직접 만들 것이 많다(보내기, 쌓아 두기, 표, 남용 막기, 90일 삭제). 소스맵을 따로 보관하고 맥에서 풀어야 오류 줄을 읽을 수 있다. 네이티브 강제 종료는 공유를 켠 사용자 것만 안다. 처리방침과 스토어 신고는 1안처럼 바뀐다(수집이므로) |
| 3안 | **Firebase Crashlytics** (`@react-native-firebase/crashlytics`) | 네이티브 강제 종료와 처리되지 않은 JavaScript 오류를 자동으로 받는다. 무료, 개수 제한 없음 | iOS를 dynamic framework로 바꿔야 한다(`expo-build-properties`, RNFB 문서: static은 prebuild 실패). 위젯, 워치, 카카오, Google, AdMob이 그대로 빌드되는지 다시 봐야 한다. Firebase 프로젝트와 `GoogleService-Info.plist`, `google-services.json`이 더 필요하다. 문서에 JavaScript 소스맵 이야기가 없어 오류 위치가 압축된 코드 줄로 보일 수 있다(확인 못 함). 바깥 회사(Google)로 보내는 것은 1안과 같다 |

### B2. 무엇을 보낼까 — **설치 ID는 모두, 사용자 ID는 로그인했을 때** (2026-10-26 사용자 결정)

ID 없이 보내면 버그는 고칠 수 있지만, 문의한 사람의 오류를 찾거나 로그인 전후 오류를 잇거나 한 사람이 되풀이해 겪는지 알 수 없다. 그래서 식별자를 붙인다.

- 보낸다: 오류 메시지와 위치, 앱 버전과 빌드 번호, OS 버전, 기기 모델, 화면 경로, 서버 요청이었으면 그 `request_id`(서버 로그와 맞춰 보는 용도).
- 식별자:
  - **설치 ID:** 모든 사용자. 앱이 설치 때 만든 무작위 값(`getDeviceId`, `src/repositories/appSettingsRepository.ts`)을 Sentry 사용자 ID로 쓴다. 다시 설치하면 새로 생겨 그 전과 이어지지 않는다.
  - **Supabase 사용자 ID(UUID):** 로그인했을 때만 더한다. 로그인하면 붙이고 로그아웃하면 뗀다.
  - 설치 ID를 광고 ID와 엮지 않는다. 엮으면 추적이 되어 ATT 동의가 필요하다.
- 보내지 않는다: 이메일, 이름, 목표와 메모 내용, 사진, 토큰. Sentry면 `sendDefaultPii: false`, 프로젝트 설정에서 IP 저장 끄기.
- **문의 번호:** 설정 화면에 설치 ID 앞부분을 「문의 번호」로 보여 주거나 문의 메일에 자동으로 넣는다. 지금 앱에는 문의 화면이 없다. 시안을 먼저 만든다.
- Sentry 보관은 30일이다. 계정을 지워도 그동안 남고, 계정이 지워지면 그 사용자 ID는 아무와도 이어지지 않는다. 처리방침에 적는다.
- Sentry 기본값에서 막아야 하는 것(2026-10-26 Sentry 문서 확인):
  - **요청 주소:** "The full request URL ... is always sent to Sentry." 요청 기록(breadcrumb)에 주소와 쿼리가 늘 들어간다. 사진 경로(`record-photos/<사용자 ID>/<파일>`)와 REST 필터 쿼리에 신고하지 않은 값이 들어갈 수 있다. `beforeBreadcrumb`에서 주소의 경로 뒷부분과 쿼리를 지운다.
  - **콘솔 기록:** "By default, the Sentry SDK sends JS console logs to Sentry which may contain PII data." 콘솔 breadcrumb을 끄거나(`console: false`), 앱의 `console` 줄에 개인정보가 없는지 본다.
  - **IP:** "the user's IP address is inferred by the Sentry backend services." 프로젝트 설정에서 IP 저장을 끄고, `setUser({ ip_address: '0.0.0.0' })`도 시험한다.
  - **Sentry 자체 설치 ID:** 네이티브 SDK가 따로 무작위 ID를 붙이는지 문서에 없다. 설치 시험에서 실제 이벤트 내용을 열어 보고, 붙으면 우리 설치 ID 하나만 남게 한다.
  - 화면 캡처와 화면 구조(view hierarchy)는 기본으로 꺼져 있다. 켜지 않는다. Session Replay도 쓰지 않는다.
- 스토어 신고가 바뀐다.
  - Apple: 「진단 › 충돌 데이터」와 「식별자 › 기기 ID」를 사용자와 연결됨, 목적은 앱 기능, 추적 아님. 로그인하지 않은 사용자도 해당한다.
  - Play: 「앱 정보 및 성능 › 비정상 종료 로그, 진단」, 「기기 또는 기타 ID」.
  - 신고 초안의 "로그인하지 않은 사용자는 기록이 기기 밖으로 나가지 않으므로 수집이 아니다"를 고친다. 기록 내용은 여전히 나가지 않지만 설치 ID와 오류 정보는 나간다.
- 처리방침 1판: 수집 항목(설치 ID, 사용자 ID, 오류 정보), 목적(오류 해결과 문의 대응), 보유 기간(30일), 수탁자와 국외 이전(개인정보 보호법 28조의8 2항의 다섯 가지: 항목, 나라와 시기와 방법, 받는 회사와 연락처, 목적과 기간, 거부 방법과 효과).

### B3. 동의가 필요한가 — **동의 없이 처리방침 고지만, 스위치 없음** (2026-10-26 사용자 결정, 아래 2안)

로그인을 필수로 바꾸는 것도 검토했지만 하지 않는다. App Review Guidelines 5.1.1(v)는 계정 기반 기능이 핵심이 아니면 로그인 없이 쓰게 하라고 한다(요약으로 받은 문구, 원문 대조 전). 개인정보 보호법 16조 1항의 최소 수집과도 부딪히고, 처음 켤 때의 강제 종료는 로그인 전에 나서 풀리지도 않는다.

B2대로면 로그인하지 않은 사용자도 설치 ID와 함께 보낸다(강제 종료는 처음 켤 때, 로그인 전에 더 많이 난다). 개인정보 보호법(2026-10-26 원문 확인)에서 수집 근거는 15조 1항의 동의(1호), 계약 이행에 필요(4호), 정당한 이익(6호) 가운데 하나다. 국외 이전은 28조의8 1항의 별도 동의(1호)나, 계약 이행에 필요한 처리위탁으로서 처리방침 공개(3호 가목)다. 오류 보고가 「계약 이행에 필요」에 들어가는지는 해석 문제라 확인하지 않았다.

이 앱은 이미 「계약 이행에 필요한 항목은 동의가 아니라 처리방침 고지로 처리한다」, 「로그인하지 않은 사용자에게는 동의를 받지 않는다」로 정했다([약관과 처리방침 설계](../specs/2026-09-30-policy-terms-design.md)). 오류 보고도 같은 틀에 넣는다. **약관은 바꾸지 않고 동의 항목도 더하지 않는다.** 바뀌는 것은 처리방침 1판뿐이다(출시 전이라 판을 올리지 않는다).

동의 방식은 오히려 문제가 생긴다. 개인정보 보호법 22조의2 1항은 "동의를 받아야 할 때" 만 14세 미만이면 법정대리인 동의를 받게 한다. 로그인하지 않은 사용자는 나이를 묻지 않으므로, 동의를 근거로 삼으면 이 조건을 맞출 수 없다.

| | 방법 | 생각할 것 |
| --- | --- | --- |
| 1안 | 처리방침 고지 + 설정에 「오류 보고 보내기」 끄기 스위치 | 처리방침에 적어야 하는 「거부 방법과 효과」(28조의8 2항 5호)를 "설정에서 끈다, 앱 사용에는 영향 없다"로 분명히 적을 수 있다. 스위치 하나와 시안이 든다 |
| **2안 (고름)** | 처리방침 고지만, 스위치 없음 | 가장 간단하다. 거부 방법은 "문의하면 그 설치 ID의 기록을 지운다, 앱을 지우면 더 보내지 않는다"로 적는다. 법이 스위치를 직접 요구하지는 않는다. 다만 거부가 번거로워 법 검토에서 지적받을 수 있다 |
| 3안 | 동의를 받는다 | 위 22조의2 문제로 로그인하지 않은 사용자에게는 쓸 수 없다. 권하지 않는다 |

어느 안이든 수집 근거(15조 1항 4호 또는 6호)와 국외 이전 근거(28조의8 1항 3호 가목)에 해당한다는 판단은 해석이다. 출시 전 법 검토에서 개인정보보호위원회 안내까지 확인한다.

### 1안(Sentry)의 순서

1. **법과 정책 먼저.** 처리방침 1판(정책 저장소)에 수집 항목(오류 정보), 수탁자(Sentry), 국외 이전(나라, 항목, 기간)을 더한다. [법령 점검](../../LEGAL-REVIEW.md) 순서로 개인정보 보호법 28조의8 인용을 확인하고, B3을 원문으로 확인한다. 스토어 신고 초안을 고친다. 사용자 확인을 받는다.
2. **Sentry 가입과 프로젝트.** 사용자가 직접 가입한다(회사 메일). 데이터 지역을 고른다. IP 저장 끄기, 알림 메일 확인. 인증 토큰은 `.secrets/`와 EAS 환경 변수 `SENTRY_AUTH_TOKEN`(sensitive)에만 둔다.
3. **설치 시험(새 worktree).** `package.json`과 `package-lock.json`을 백업하고 설치한 뒤 `npm ls react-dom --all`이 `19.2.3` 하나인지 본다. 설정 플러그인, Metro 설정, `Sentry.init`(`sendDefaultPii: false`, `beforeBreadcrumb`로 주소 정리), 설치 ID와 로그인 사용자 ID 붙이고 떼기, `ErrorBoundary`와 연결.
4. **설정 화면.** 「문의 번호」 한 줄. 끄기 스위치는 두지 않는다(B3). 시안을 먼저 아티팩트로 보여 준다.
5. **확인.** 시뮬레이터 Release 빌드와 TestFlight에서 일부러 JavaScript 오류와 네이티브 강제 종료를 낸다. Sentry에서 원래 코드 줄로 보이는지, 설치 ID가 붙는지, 로그인하면 사용자 ID가 붙고 로그아웃하면 떨어지는지, IP와 이메일과 사진 경로가 없는지 본다. Sentry에서 한 설치 ID의 기록을 지울 수 있는지도 시험한다(B3 거부 방법). `qa`와 `security` 에이전트로 검토한다.
6. **기록.** DEV-SETUP에 오류 보는 법, RELEASE-CHECKLIST에 주 1회 보기.

## 순서와 이번에 하지 않는 것

- **순서:** A를 먼저 한다(서버만 바꾸고 정책 변경이 없다). B는 B1, B2, B3을 정한 뒤 정책 문서부터 한다. 둘 다 운영 빌드(TestFlight) 전에 끝내는 것이 좋다. B는 앱 코드라 운영 빌드 일정에 영향이 있다.
- **하지 않는 것:**
  - 사용 분석(어떤 화면을 얼마나 쓰는지). 수집 목적이 달라 따로 정한다.
  - 성능 추적(Sentry tracing, 화면 속도). 오류가 먼저다.
  - 대시보드. 나중에 만들 때 `~/logs/`, Healthchecks.io API, Sentry API를 읽게 한다.
  - 함수 로그 문구 바꾸기. 모아 보고 부족하면 그때 고친다.

## 확인 못 한 것

- PostgREST가 5xx일 때 실제로 줄을 남기는지. A 6번에서 본다.
- `docker logs --since --until`로 잘라 모을 때 경계에서 줄이 빠지거나 겹치지 않는지. A 1번을 만들 때 시험한다.
- DB 설정이 복구한 DB에 따라오는지. `ALTER SYSTEM`은 데이터 폴더에 저장되고 백업은 `pg_dump`라 따라오지 않을 것으로 본다. 복구 순서에 한 줄 더한다.
- Sentry가 Expo 57, RN 0.86, 이 저장소의 `react-dom` 고정과 함께 설치되는지. 무료 요금제에서 데이터 지역을 고를 수 있는지.
- Xcode Organizer 충돌 보고가 Apple 신고 예외(「Apple이 모으는 데이터」)에 해당하는지 App Store Connect 도움말로 다시 확인.
- Sentry에서 특정 설치 ID나 사용자 ID의 기록만 골라 지울 수 있는지. 안 되면 처리방침의 거부 방법을 "30일 뒤 자동으로 지워지고, 앱을 지우면 더 보내지 않는다"로 바꾸고 법 검토에서 충분한지 본다.
- 오류 보고가 개인정보 보호법 15조 1항 4호나 6호, 28조의8 1항 3호 가목에 해당해 따로 동의 없이 보내도 되는지(B3). 출시 전 법 검토에서 개인정보보호위원회 안내까지 확인.
