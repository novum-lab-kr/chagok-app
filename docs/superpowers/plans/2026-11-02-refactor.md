# 리팩터링 계획 (2026-11-02 승인. 1~3단계는 2026-11-03 끝남, 4~5단계는 1.0.2 이후)

화면 동작은 바꾸지 않는다. 같은 일을 하는 코드를 한곳으로 모아, 다음에 한쪽만 고쳐 어긋나는 일을 막는 것이 목적이다.

## 언제, 어디서

- **구독 결제 연결을 커밋한 뒤에 시작한다.** 1단계와 2단계가 고치는 `app/(tabs)/settings.tsx`, `app/subscription.tsx`, `app/account/delete.tsx`는 구독 worktree에서 아직 커밋하지 않은 파일이다. 먼저 하면 충돌한다.
- 브랜치는 `refactor/shared-flows`이고, 구독 브랜치의 마지막 커밋에서 만든다. 단계마다 확인한 뒤 따로 커밋한다.
- 1.0.1에는 1단계부터 3단계까지만 넣는다. 4단계와 5단계는 출시 뒤 1.0.2에서 한다.

## 단계별 계획

### 1단계. 로그아웃과 계정 삭제의 기기 정리를 함수 하나로 (1.0.1)

- **지금:** `settings.tsx` 116~131줄과 `account/delete.tsx` 64~79줄이 같은 다섯 단계를 같은 순서로 부른다. 세션 지우기, 카카오 로그아웃, Google 로그아웃, 결제 계정 익명 전환, 기기 비우기 순서다. 끝난 뒤 처리(`resetUser`, `setErrorUser(null)`, `resumeSync`)도 같다. 결제 계정 전환이 기기 비우기보다 먼저여야 한다는 보안 검토 L1 순서가 두 곳에 복사돼 있다. `connect.tsx` 189줄과 337줄에도 카카오와 Google 로그아웃 두 줄이 있다.
- **바꾸는 것:**
  - `src/app-data/signOut.ts`(새 파일)에 세 함수를 둔다.
    - `clearSignInSessions(supabase)`: 세션, 카카오, Google 로그아웃.
    - `signOutAndWipe(supabase)`: `clearSignInSessions`, 결제 계정 익명 전환, 기기 비우기를 순서대로 부른다.
    - `afterSignedOut()`: 끝난 뒤 처리 세 줄.
  - 두 화면과 `connect.tsx` 두 곳은 이 함수만 부른다. 계정 삭제의 서버 삭제와 Google 연결 끊기는 화면에 그대로 둔다(삭제에만 있는 단계다).
- **테스트:** 새 `__tests__/signOut.test.ts`에서 부르는 순서를 기록해, 결제 전환이 기기 비우기보다 먼저인지 확인한다. 한 단계가 실패하면 뒤 단계를 부르지 않는지도 본다.
- **확인:** 시뮬레이터에서 로그아웃과 계정 삭제를 한 번씩 한다(개발 서버 테스트 계정을 쓰고, 지우기 전에 묻는다).
- 효과 큼, 위험 중간.

### 2단계. 결제 결과 안내와 구매 복원을 함수 하나로 (1.0.1)

- **지금:** 「취소면 아무것도 안 하고, 대기면 대기 안내, 아니면 실패 안내」 분기가 세 곳에 있다(`settings.tsx` 66줄, `subscription.tsx` 47줄, `stickers/pack/[packId].tsx` 66줄). 복원 흐름(실패 안내, 결과 안내)은 두 곳에 있다(`settings.tsx` 68~82줄, `subscription.tsx` 54~65줄).
- **바꾸는 것:** `src/app-data/purchaseDialogs.ts`(새 파일)에 두 함수를 둔다.
  - `notifyBuyFailure(ask, result, failedDialog)`: 실패 결과만 받아 안내한다.
  - `restoreWithDialog(ask)`: 복원하고 결과를 안내한다. busy 표시는 화면이 넘긴 콜백으로 한다.
- **테스트:** 취소, 대기, 실패 세 경우에 어떤 안내를 띄우는지 확인하는 단위 테스트를 둔다.
- **확인:** 개발용 「시험 결제」 창에서 성공, 실패, 대기, 취소를 한 번씩 눌러 본다.
- 효과 중간, 위험 작음.

### 3단계. 작은 중복 정리 (1.0.1)

| 무엇 | 지금 | 바꾸는 것 |
| --- | --- | --- |
| 월 키 | `goalRepository.ts` 276줄과 `widgets/snapshot.ts` 94줄이 `연-월` 글자를 직접 만든다 | `domain/dates.ts`의 `monthKeyOf`를 쓴다 |
| 날짜 차이 | `sync/accountStatus.ts` 62~63줄이 0시로 맞춘 뒤 하루 길이로 나눈다 | `domain/dates.ts`에 `daysBetween`을 더해 쓴다 |
| 구독 상태 타입 | `purchases/index.ts` 16줄과 `domain/subscription.ts` 32줄에 같은 모양이 두 번 있다 | domain에 하나만 두고 purchases가 가져다 쓴다 |
| 금액 글자 | `purchases/price.ts`의 `priceLabel`과 `app-data/subscriptionViews.ts`의 `moneyLabel`이 원화 규칙을 따로 갖는다 | `price.ts`에 `formatAmount` 하나를 두고 둘 다 쓴다 |
| 닫힘 대기 시간 | `DISMISS_FALLBACK_MS = 700`이 `useDialog.ts`와 `account/delete.tsx`에 따로 있다 | `useDialog.ts`에서 내보내 함께 쓴다 |
| 묶음 상태 타입 | `type PackState = Awaited<ReturnType<typeof loadPackState>>`가 화면 세 곳에 있다 | `packRepository.ts`에서 `PackState`로 이름을 붙여 내보낸다 |
| 서버 관리자 클라이언트 | Edge Function 세 곳이 같은 코드로 만든다 | `_shared/auth.ts`에 `adminClient()`를 둔다. 운영 함수 배포는 1.0.1 서버 반영 때 함께 한다 |

- 효과는 항목마다 작고, 위험도 작다. 테스트, 타입 검사, 번들로 확인한다. 서버 함수는 `npm run test:server`로 확인한다.

### 4단계. 화면이 다시 읽는 코드를 훅 하나로 (1.0.2)

- **지금:** 포커스 때 읽기, alive 플래그, 시도 번호, eslint 예외 줄이 똑같이 8개 화면에 있다.
- **바꾸는 것:** `src/app-data/useFocusLoad.ts`를 만들어 8곳을 바꾼다. 한 번에 다 바꾸지 않고 두세 화면씩 바꾼 뒤 시뮬레이터에서 화면 전환을 확인한다.
- 효과 중간, 위험 작음에서 중간 사이(화면마다 다시 읽는 조건이 조금씩 다르다).

### 5단계. 큰 화면 나누기, 위젯과 워치 공통 코드 (1.0.2 이후)

- **계정 연결 화면:** `connect.tsx`(418줄)의 `connect()`(110줄)에서 화면이 없는 단계(로그인, 동의 확인, 연결 계획 실행)를 `src/app-data/connectFlow.ts`로 뺀다. 화면 안의 DB 쿼리(290줄)는 `src/sync/account.ts`로 옮긴다. 취소와 시도 번호 처리가 섬세해서 계정 화면 전체를 다시 확인해야 한다. 위험이 크다.
- **판 화면:** `goal/[id]/index.tsx`의 `place()`에서 붙인 뒤 처리(첫 스티커 안내, 사용 기록 동의)를 따로 뺀다.
- **위젯과 워치:** 두 벌로 있는 앱 상태 감지, 요청 중복 제거, 달력 칸 계산, 잠김 계산을 `src/widgets`의 공통 함수로 모은다. 실기기 위젯과 워치 확인이 필요하다.

## 하지 않는 것

- `src/design-system/`은 domain, repositories, app-data를 가져다 쓰지 않는다(Storybook에서 혼자 그리기 위해서다). 그래서 디자인 시스템 안의 날짜 계산 중복(`calendarDateKey`, `dayAfter`)과 `SubscriptionPlan` 타입은 그대로 둔다.
- knip이 「안 쓰는 export」로 잡은 27개는 모두 자기 파일 안에서 쓰인다. `export`만 떼는 일은 효과가 없어 하지 않는다.
- 화면이 repositories를 직접 부르는 곳은 많지만 지금은 사실상의 관례라 한꺼번에 바꾸지 않는다. 5단계에서 손대는 화면만 바꾼다.
