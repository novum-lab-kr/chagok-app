# 함께 목표 설계

2026-11-04. 친구와 같은 목표를 함께 채우는 기능이다. **1.1.0 다음 버전**에 넣는다(1.1.0은 2026-11-04 함께 목표 없이 심사에 올린다). 동작의 원본은 [PRD](../../PRD.md) 4.15이고, 이 문서는 서버, 데이터, 정책, 규모를 적는다. PRD와 다르면 PRD가 우선한다.

- 시안: [함께 목표](https://claude.ai/artifact/6ar4PMAu3UFt7grFTGGqio)(비공개, 9판). 원본은 `docs/design/proposals-2026-10/friends-goal.template.html`, 다시 만들기는 `node docs/design/proposals-2026-10/friends-goal.gen.mjs <캡처 폴더> <출력 html>`. 캡처는 실제 컴포넌트를 렌더한 임시 스토리에서 찍었다(커밋하지 않음).
- 고른 안은 아티팩트 db `review/choice-fg-*`에 있다: 처음 낼 방식 `scope=a`(세 가지 모두), 위젯과 워치 `widget=a`, 초대 링크 `link=a`(기간 없음), 판 배치 `layout=a`.
- 출발점이 된 아이디어: [친구와 함께 쓰기: 아이디어](2026-10-17-friends-ideas.md). 「방」은 만들지 않기로 했다(시안이 방, 판 두 종류, 설정 셋으로 불어나 흐름이 어지러워졌다).

## 1. 무엇을 만드나

「방」 없이 **목표 하나를 여럿이 함께** 한다. 목표 탭과 판 화면 구조는 그대로 두고, 함께하는 목표만 판 아래에 친구들이 보인다.

| 방식 | 시작하는 곳 | 판 | 연결 없이 붙이기 |
| --- | --- | --- | --- |
| 각자 판에 | + → [친구와 함께] → 「각자 판에」 | 사람마다 자기 판. 내 판 아래에 친구 판 | 된다 |
| 한 판에 같이 | + → [친구와 함께] → 「한 판에 같이」 | 판 하나에 각자 스티커 | 안 된다 |
| 내 목표 보여주기 | 내 목표의 목표 설정 → [보여줄 친구 초대하기] | 내 판을 친구가 보기만 | 된다(보여주는 쪽) |

## 2. 지키는 원칙 (PRD 2절과의 관계)

PRD 2절은 「타인의 판정」과 「소셜 경쟁」, 「재촉 문구」를 뺀다. 함께 목표는 이 원칙 안에서 만든다.

- **비교로 읽히지 않게:** 함께하는 판에는 진행 막대가 없다. 친구 판에 칸 수, %, 순위를 쓰지 않는다. 친구 순서는 들어온 순서다.
- **재촉하지 않게:** 누가 붙였다는 알림을 보내지 않는다. 위젯에 친구 소식을 띄우지 않는다(위젯 B안을 고르지 않은 이유).
- **판정하지 않게:** 친구가 내 칸을 확인하거나 승인하는 장치가 없다. 반응(좋아요, 댓글)도 없다.
- **보이는 것은 최소:** 친구에게 보이는 것은 이름, 스티커, 판에 붙은 칸이다. 사진과 메모는 나만 본다.

## 3. 화면 요약

자세한 동작은 PRD 4.15. 화면 수치는 확정 시안 기준이다.

- **각자 판 화면:** 진행 막대 없음. 위에 내 판(4칸 두 줄, 판 안 폭 330 이상이면 5칸, ‹ ›로 넘김). 아래에 「함께하는 사람 n」과 줄 목록 `[이름 배지][얇은 판]`.
  - 친구 적립판: 7칸 두 줄, 판 안 폭 320 이상이면 8칸. 가장 최근 칸이 둘째 줄에 오도록 연다. 옆으로 밀면 앞 칸.
  - 친구 달력판: 두 주(지난주, 이번 주), 늘 7칸. 내 달력판도 두 주만 보인다.
  - 이름 칸 폭 56, 칸 높이 32, 스티커 24. 줄을 누르면 그 친구 판 전체를 크게(보기만).
  - 친구가 아직 없으면 「친구를 기다리고 있어요」와 [링크 다시 보내기].
- **한 판 화면:** 판 위에 사람 줄(스티커 + 이름 배지). 칸마다 붙인 사람의 스티커. 친구 칸을 누르면 누가 언제 붙였는지만. 연결이 없으면 붙이지 않고 알린다.
- **얇은 판 프레임:** 내 판 프레임과 같은 겹(바깥 잉크, 틈, 반투명 띠, 안쪽 잉크, 계단 모서리)을 두께 2, 1, 1, 1로. 디자인 시스템 `PixelFrame`에 모양을 하나 더한다(기존 값은 그대로).
- **목표 탭:** 함께 목표 카드에 「n명이 함께」. 보여주기로 받은 목표는 「보기만」.
- **기록 탭:** 그대로. 함께 목표에 남긴 내 기록도 내 기록이다.

## 4. 데이터

나중에 메모, 사진, 인원을 늘릴 수 있게 둔다(2026-11-04 사용자 요청: 「나중에 메모, 사진까지 넣을 계획이 있고 사람도 늘릴 수도 있으니깐 그거 고려해서 확장성을 가지고 설계해」).

| 테이블 | 열 | 비고 |
| --- | --- | --- |
| `shared_goals` | id, 방식(`each`, `one`, `show`), 이름, 판 종류, 칸 수 또는 종료일, 만든 사람, 최대 인원, 만든 시각과 고친 시각, 지운 시각 | 최대 인원은 열이라 서버에서 바꾼다(지금 6) |
| `shared_goal_members` | 함께 목표, 사용자, 이름, 스티커, 역할(`owner`, `member`, `viewer`), 들어온 시각, 나간 시각, 내 목표 id | 같은 목표 안에서 스티커 겹침 금지(유일 제약) |
| `shared_goal_invites` | 함께 목표, 코드, 만든 시각, 끈 시각 | 기간 없음. [초대 링크 새로 만들기]가 옛 코드를 끈다 |
| `shared_goal_reports` | 함께 목표, 신고한 사람, 대상 사람, 사유, 시각, 처리 상태 | 운영자가 본다 |
| `profiles_defaults` | 사용자, 마지막으로 쓴 이름, 스티커 | 다음 함께 목표에 채워 준다. 따로 프로필 화면은 없다 |

- **칸(스티커)에 보이는 범위:** 스티커 행에 `visibility`(`self`, `members`)를 둔다. 지금은 스티커 칸 자체는 `members`, 기록(사진, 메모)은 늘 `self`로만 쓴다. 나중에 기록 나누기를 넣으면 기록 쪽에도 같은 열을 쓴다.
- **각자 판:** 사람마다 지금과 같은 내 목표 행이 있고 `shared_goal_members.내 목표 id`로 잇는다. 그래서 위젯, 워치, 오프라인 붙이기가 지금 코드 그대로 돈다. 친구 판은 서버에서 읽기만 한다(RLS: 같은 함께 목표의 나가지 않은 멤버만 읽기).
- **한 판:** 칸은 서버가 주인이다. 같은 칸에 두 사람이 붙이면 서버 유일 제약으로 하나만 들어가고 나중 사람에게 알린다. 달력판은 같은 날 두 장까지 겹쳐 붙는다.
- **보여주기:** 보는 사람은 `viewer` 역할. 내 목표와 스티커 칸만 읽고 기록은 읽지 못한다.
- **동기화:** 지금 백업 대기열(PRD 5절)을 그대로 쓴다. 친구 판은 판 화면을 열 때와 앞으로 올 때 받아 오고, 실시간 구독은 한 판 화면에만 쓴다.
- **로그인 필요:** 함께 목표는 서버가 있어야 해서 로그인한 사용자만 만들고 들어온다. 로그인 전이면 먼저 로그인을 권하고, 지금 목표와 기록은 그대로 둔다.
- **한 번에 한 기기(PRD 12절 10-05)와의 관계:** 기기 규칙은 사람 단위다. 다른 사람이 같은 판에 붙이는 것은 그 규칙과 별개로 서버 제약이 막는다.

## 5. 초대 링크

- 주소 하나(예: `chagok.novum-lab.com/invite/K7Q2MX`). 기간 없음. 만든 사람이 [초대 링크 새로 만들기]를 누르면 옛 주소로는 들어올 수 없다.
- 앱이 있으면 앱이 열리고(유니버설 링크, 앱 링크), 없으면 스토어로 간다. 정책 사이트(novum-web)에 앱 연결 파일을 둔다.
- 받은 사람이 로그인 전이면 「은주님이 함께하자고 했어요」와 로그인. 로그인 뒤 미리보기, 내 이름, 내 스티커 → [함께하기].
- 자리가 다 찼거나, 목표가 지워졌거나, 링크가 바뀌었거나, 내보내진 사람이면 문제 화면(차곡이 + 설명).

## 6. 정책

**App Store 심사 지침 1.2(사용자 생성 콘텐츠).** 이름은 다른 사용자에게 보이는 사용자 생성 콘텐츠다. 지침이 요구하는 네 가지를 갖춘다.

| 요구 | 함께 목표에서 |
| --- | --- |
| 부적절한 내용 거르기 | 이름에 금칙어 거르기(서버). 사진과 메모는 나누지 않는다 |
| 신고와 빠른 대응 | 목표 설정 「문제가 있을 때」 → [신고하기]. 운영자가 확인하고 대상을 내보낼 수 있다 |
| 괴롭히는 사용자 막기 | 누구든 [사람 차단하기](아래), 만든 사람은 [내보내기], 누구든 [이 목표에서 나가기] |
| 연락 방법 | 설정 「도움말과 정보」의 문의하기(이미 있음) |

**차단(2026-11-04 결정).** 사용자가 「지인을 초대해서 쓰는건데 … 차단? 이게 있어야된다고?」라고 물었다. 1.2 원문은 적용 대상을 「Apps that enable users to create, generate, upload, share, or otherwise contribute content」로 쓰고 초대제 예외가 없어, 가볍게 넣기로 했다(시안 9판 「차단」).

- 목표 설정 「문제가 있을 때」 [사람 차단하기] → 사람 고르기 시트 → 확인(기존 `PixelDialog`).
- 차단하면 서로의 판, 이름, 스티커가 보이지 않는다. 다른 사람에게는 둘 다 보인다. 서로가 만든 함께 목표에 들어갈 수 없고, 제삼자의 목표에서 만나면 서로 가려진다.
- 상대에게 알리지 않는다. 차단당한 사람이 초대 링크를 열면 「들어갈 수 없어요」(차단을 드러내지 않음).
- 만든 사람이 차단하면 내보내기와 같다. 한 판에서 차단한 사람의 칸은 이름 없는 흐린 칸(자리는 지킨다).
- 앱 설정 「차단한 사람」에서 푼다. 풀면 함께하던 목표에서 다시 보인다.
- 데이터: `user_blocks`(차단한 사람, 차단된 사람, 시각). 친구 판 읽기 규칙(RLS)과 초대 수락에서 양쪽 방향을 모두 거른다.

**개인정보 보호법과 약관.** 다른 사용자에게 이름, 스티커, 칸이 보이므로 처리방침과 약관을 고친다. 1.1.0의 약관 2판과 처리방침 2판(2026-11-04 게시, 같은 날 시행)에는 넣지 않았고, 함께 목표를 내는 버전에서 다음 판(약관 3판, 처리방침 3판)으로 낸다. 문안 초안은 [friends-goal-policy-draft/](friends-goal-policy-draft/)(약관 2판, 처리방침 작업본 기준 패치): 약관 제2조 정의, 제4조 6~7항, 제6조 2항(「이용자가 고르지 않은 사람에게 공개하지 않습니다」), 제7조 금지 행위, 제7조의2 신고와 차단과 이용 제한, 제9조 계정 삭제 시 함께 목표, 제13조. 처리방침 2절 항목, 5절 보유 기간, 6절 2항(함께하는 사람에게 보이는 정보), 8절 Google 신고 알림. 그때 이용자가 있으면 불리한 변경(금지 행위, 이용 제한)은 30일 전에 알린다. 초안의 제9조는 만든 사람이 계정을 지우면 가장 먼저 들어온 사람이 이어받는다고 적었다(추천안, 사용자 확인 전).

## 7. 위젯과 워치

- **위젯(A):** 지금처럼 내 판에 붙인다. 함께 목표면 「4명」 작은 표시만 더한다. 위젯은 친구 소식을 받아 오지 않고 앱이 쓴 값만 읽는다. 한 판 목표는 연결돼 있을 때만 붙고, 아니면 앱을 연다.
- **워치:** 지금 그대로. 함께 목표도 목록에 다른 목표와 같이 보이고, 내 판에 붙이고, 차곡이 블록은 내 스티커만 쌓인다.

## 8. 규모 (시안 기준 추정)

| 일 | 대략 |
| --- | --- |
| 서버: 테이블, RLS, 초대, 신고, 금칙어, 한 판 칸 제약 | 3~5일 |
| 초대 링크: 앱 연결 파일, 스토어로 보내기 | 1~2일 + 외부 설정 |
| 앱: + 시트, 친구와 함께, 초대 받기, 판 화면 두 종류, 크게 보기, 보여주기, 목표 설정, 문제 화면, 동기화 | 8~11일 |
| 위젯 「n명」 표시 | 반나절 |
| 차단: 표, 읽기 규칙, 설정 화면 | 1일 |
| 문서, 처리방침과 약관 새 판, 두 사람 흐름 확인 | 3일 |

세 방식 모두 약 3.5~4주.

## 9. 운영 기본값 (2026-11-04, 에이전트가 정함)

사용자가 「3번은 내가 다 정해야돼?」라고 물어, 흔한 방식을 따라 에이전트가 정했다. 바꾸려면 이 절을 고친다.

- **금칙어:** 거르는 장치(서버 검사)는 함께 목표와 함께 넣고, 목록 내용은 나중에 채운다(2026-11-04 사용자: 「금칙어는 지금 굳이 안정해도 될꺼 같아」). 지침 1.2가 거르는 방법을 필수로 요구해서 장치는 빼지 않는다. 심사 제출 전에 목록을 채운다. 외부 목록을 가져오지 않고(사용권 확인 부담) 우리 목록을 서버 표 `banned_words`에 둔다. 앱 업데이트 없이 늘린다. 목표 이름과 사람 이름을 저장할 때 서버에서 검사한다. 비교 전에 NFKC 정규화, 공백과 기호 빼기, 소문자로 맞춘다. 걸리면 「다른 이름을 써 주세요」. 목록이 다 잡지 못하는 것은 신고로 받는다.
- **신고:** `shared_goal_reports`에 저장하고, 서버 함수가 문의 메일 주소(`SUPPORT_EMAIL`, `src/support/contactMail.ts`)로 알림 메일을 보낸다. 우리 목표는 **24시간 안에** 확인하고 필요하면 이름을 지우거나 그 사람을 내보내는 것이다. 지침 원문은 「timely responses」라 숫자를 정하지 않는다. 24시간은 우리 기준이다.
- **초대 링크 주소:** `https://chagok.novum-lab.com/invite/<코드>`(사용자가 고름. `j`는 뜻이 안 보여 바꿨다). 이미 정책 문서를 게시하는 우리 도메인이다(`src/policy/urls.ts`).
- **링크가 여는 것:** 웹 주소 모양의 딥링크다(iOS 유니버설 링크, Android 앱 링크). 앱이 깔려 있으면 OS가 브라우저를 거치지 않고 앱을 바로 열고, 앱이 코드를 읽어 초대 흐름(로그인 전이면 「은주님이 함께하자고 했어요」 → 로그인 → 함께하기)으로 간다. 앱이 없으면 같은 주소의 웹 페이지가 열려 스토어로 보낸다. `chagok://` 주소를 쓰지 않는 이유: 앱이 없으면 아무것도 열리지 않고, 메신저가 링크로 인식하지 않을 수 있고, 다른 앱도 같은 이름을 쓸 수 있다.
- **필요한 것:** 그 도메인에 `apple-app-site-association`(iOS)과 `assetlinks.json`(Android)을 올리고(novum-web 쪽 일), 앱 설정에 연결 도메인을 더한다. 웹 페이지에는 [앱에서 열기](`chagok://invite/<코드>`)와 스토어 버튼을 둔다. 메신저 안 브라우저는 유니버설 링크를 앱으로 넘기지 않는 경우가 있다고 알려져 있어 버튼으로 받친다(원문 확인 못 함).
- **설치 직후:** 스토어를 거쳐 처음 깐 앱은 초대 코드를 알 수 없다(따로 서비스를 쓰지 않으면). 웹 페이지가 「앱을 설치한 뒤 이 링크를 다시 눌러 주세요」를 보인다.
