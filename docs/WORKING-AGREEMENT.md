# 작업 방식

이 저장소에서 에이전트가 따를 규칙이다. 지금까지 실제로 효과가 있었던 것만 적었다.

## 1. 결정과 작성을 분리한다

**결정이 필요한 것을 먼저 모아 묻고, 그다음에 쓴다.** 앞선 결정이 뒤의 산출물을 규정하기 때문에
순서를 뒤집으면 두 번 쓰게 된다. 예: 달력판 월 경계 정책이 정해져야 데이터 모델 델타를 쓸 수 있었다.

**임의의 숫자나 동작으로 미확정을 메우지 않는다.** PRD에 `미확정`으로 남기고, 정해지면 날짜
스탬프와 함께 확정 이력에 옮긴다. 테스트 통과나 문서의 baseline 표기를 **사용자 승인으로 해석하지
않는다.**

## 2. 시각 작업은 렌더해서 눈으로 보고 고친다

좌표만 계산하고 결과를 안 보면 거의 틀린다. 이 저장소에서 실제로 세 번 헛돌았다 — 런닝 인물이
진저브레드 쿠키로, 따봉이 얹힌 막대로, 운동화가 슬리퍼로 나왔는데 **렌더해보니 1초 만에 보였다.**

```sh
playwright screenshot --full-page --viewport-size "1000,800" "file://$PWD/preview.html" out.png
```

그다음 이미지를 직접 열어서 본다.

- 큰 크기(180px)와 **실제 사용 크기(56px)를 한 페이지에** 같이 깔아 비교한다
- 변형안은 **3~4개를 한 번에** 만들어 나란히 렌더한다. 하나씩 고치면 왕복만 늘어난다
- `outline:1px dashed`로 경계를 표시해 **아이콘 간 시각 무게**가 고른지 본다
- 잘 나온 것을 기준선으로 삼고 "무엇이 다른가"를 본다

## 3. 선택지는 말로 설명하지 말고 보여준다

"A안은 이렇고 B안은 저렇습니다"보다 **세 개를 나란히 렌더해 아티팩트로 발행**하는 쪽이 훨씬 빨리
결정된다. 홈 구조, 달력 월 경계, 따봉 모양 모두 이 방식으로 정해졌다.

## 4. 타입 체크로는 부족하다

`tsc --noEmit`이 통과해도 런타임에 깨질 수 있다. 화면 코드를 만졌으면 **실제 번들까지 돌린다.**

```sh
npx expo export --platform ios --output-dir /tmp/check && rm -rf /tmp/check
```

## 5. 도메인 로직은 TDD로

`slots.ts`, 리포지토리, 어댑터처럼 UI 없는 계층은 실패하는 테스트부터 쓴다. 특히 **타입으로 못 잡는
경계**를 테스트로 고정한다.

- 칸 번호는 1부터, `slotIndex`는 0부터 (off-by-one)
- 달력 키는 로컬 시간. `toISOString()`은 자정 근처에서 하루를 민다

## 6. 디자인 시스템을 재해석하지 않는다

`src/design-system/`의 팔레트·프레임·토큰은 사용자가 승인한 기준이다. **추가는 하되 기존 값을
바꾸지 않는다.** 도메인과 화면의 데이터 모양이 다르면 어느 한쪽을 비틀지 말고
`src/app-data/pocketAdapter.ts` 같은 **어댑터로 흡수**한다.

새 prop은 **선택(optional)으로** 추가해 기존 Storybook 스토리가 계속 렌더되게 한다.

## 7. 코드 작성 전에 버전 문서를 읽는다

루트 `AGENTS.md` 지시다. Expo 57은 이전 버전과 다르다.
`https://docs.expo.dev/versions/v57.0.0/`를 먼저 확인한다. 실제로 이 습관이
`PRAGMA user_version` 마이그레이션 패턴을 찾아줬다.

## 8. 커밋은 덩어리로 나눈다

설정 / 코드 / 문서·에셋을 섞지 않는다. 문서에 PNG가 수십 장 들어가면 코드 diff가 묻힌다.
커밋 메시지에는 **무엇을 왜 그렇게 했는지**를 적는다 — 특히 우회한 제약과 그 이유.

## 9. 막힌 것은 숨기지 않는다

실패한 명령, 미검증 항목, 추측으로 넘어간 부분을 결과 보고에 그대로 적는다.
"실기기 검수 미수행"처럼 **확인하지 않은 것을 확인한 것처럼 쓰지 않는다.**

## 10. 되돌리면 안 되는 것

- `package.json`의 `overrides: { "react-dom": "19.2.3" }` — 지우면 모든 `npm install`이 ERESOLVE로 실패한다
- `jest-expo`를 쓰지 않는 것 — 같은 react-dom 충돌을 일으킨다. `jest` + `ts-jest`가 맞다
- `src/stickers/catalog.ts`(22종) — 참조하는 코드는 없지만 **마이그레이션 매핑 근거**다. 임의 삭제 금지
- `.omc/` — 세션마다 바뀌는 도구 상태. 커밋하지 않는다

## 11. 사용자와 일하는 방식

사용자가 직접 지시한 것들이다. 규칙의 원본은 저장소(AGENTS.md와 이 절)이고, 에이전트의 로컬 메모리에는 이 맥에서만 맞는 정보만 둔다(2026-10-18).

- **한국어로 쓴다.** 최종 보고뿐 아니라 도구 호출 사이 진행 메모, 질문 앞 설명까지 사용자가 읽는 글은 모두 한국어다. 커밋 메시지는 저장소 관례(영어)를 따른다(2026-09-28).
- **쉬운 말로 쓴다.** "spike" 대신 "시험 구현"처럼 풀어 쓰고, 시험 구현인지 실제 구현인지 늘 밝힌다.
- **작업마다 새 worktree와 브랜치를 먼저 만든다.** main 체크아웃은 다른 세션과 같이 쓴다. 문서 초안도 첫 파일을 쓰기 전에 만든다. 끝난 worktree는 정리한다.
- **가운뎃점(·)으로 낱말을 잇지 않는다.** 앱 문구, 위젯, 워치, 시안, 답변 모두 해당한다. 낱말이나 온전한 문장으로 쓰고, 꼭 붙여야 하면 라벨을 따로 디자인한다. 시안을 내기 전에 `·`를 검색한다(2026-10-15).
- **push가 끝나면 정리한다.** main에 합쳐 push하면 그 worktree와 로컬 브랜치를 묻지 않고 지우고, 그 worktree에서 띄운 서버도 끈다(2026-10-11).
- **사용자가 보는 개발 서버는 8081 하나다.** 작업마다 포트가 바뀌면 폰에서 헷갈린다. 8081을 다른 worktree로 바꾸기 전에 지금 무엇이 떠 있고 무엇으로 바꿀지 말하고 허락을 받는다(2026-10-13).
- **새 worktree를 만들면 먼저 정리한다.** 기능이 main에 합쳐져 push될 때마다 문서, 시안, 코드에 지난 흔적이 쌓여 한꺼번에 치우기 어려워졌다. 다음 worktree를 만든 직후 그 작업 전에 문서 최신화, 오래된 내용 폐기, 반영된 시안 정리, 쓰지 않는 코드 정리를 하고, 정리만 담은 커밋을 따로 남긴다. 순서는 AGENTS.md 「새 worktree를 만들면 먼저 정리한다」(2026-10-18).
- **시안 메모에는 모두 답한다.** 범위 밖으로 보이는 메모도 반영하거나 이유를 말한다.
- **애매하면 선택지 3개를 준다.** 결정이 필요한 점마다 3안을 내고 하나를 추천으로 표시해 사용자가 고르게 한다. 한 번에 묻는 질문은 4개 이하. 사용자가 선택지 밖의 새 방향을 말하면 그 방향 안에서 다시 3안을 낸다(2026-09-28).
- **커밋은 확인 뒤에 한다.** 계획·설계 문서는 승인 뒤에 커밋한다. 코드는 계획이 승인돼도 바로 커밋하지 않고, 사용자가 실제로 돌려 본 뒤(Expo Go·Storybook 등) 커밋한다. 테스트·타입 체크 통과는 확인으로 치지 않는다. 스킬이나 계획이 "태스크마다 커밋"이라고 해도 이 규칙이 우선한다(2026-09-30, 2026-10-02). main에는 브랜치 단위로 `--no-ff` 병합한다. push는 사용자가 요청할 때만 한다.
- **화면 문구는 사용자 관점으로 쓴다.** 시스템 상태·내부 개념(세션 만료, 변경·outbox, 서버 거부, 동기화)이 아니라 사용자가 할 일과 결과를 말한다. 예: "로그인이 풀렸어요" → "로그인이 필요해요", "변경 3개를 올리지 못했어요" → "아직 백업하지 못한 기록이 있어요"(2026-10-01).
- **시안은 아티팩트로 먼저, Storybook은 확정 뒤에.** 시안을 보여 달라고 하면 Storybook 코드를 만들지 않고 아티팩트를 발행한다. 형식은 안마다 설명·좋은 점/걸리는 점·[이 안 고르기]·메모 칸, 비교용 현재안(고를 수 없음), 아래 고정 막대에 고른 안과 [메모까지 복사]다. 고른 안과 메모는 아티팩트 `db`에 저장해 에이전트가 읽는다. 시안이 모두 확정되면 그때 Storybook·컴포넌트에 반영한다(2026-10-03). 예시와 원본은 [design/proposals-2026-10/](design/proposals-2026-10/README.md).
- **화면 흐름도는 화면과 같이 바꾼다.** 화면 기획이나 디자인이 바뀌어 Storybook 스토리를 추가·변경·삭제하거나 이동 경로가 바뀌면, 같은 작업 안에서 `Flows/앱 전체`(노드·화살표·자리·PRD 태그)도 맞춘다. 시안 확정 → Storybook 반영 → 흐름도 반영 순서다. 기획만 있고 화면이 없으면 빈 노드(빨간 점선)로 둔다. 방법은 [stories/flows/README.md](../stories/flows/README.md)(2026-10-04).
- **브랜드·캐릭터는 묻고 시작한다.** 새싹이는 기본 스티커일 뿐 메인 캐릭터가 아니다. 대표 이미지를 추측하지 않는다(2026-10-03). 확정 캐릭터는 [design/character/](design/character/README.md).
- **계정·외부 설정이 필요한 일은 뒤로 미룬다.** 지금 개발할 수 있는 일을 먼저 고른다(2026-10-01, 2026-10-10 다시 확인). Apple은 2026-10-05 승인됐다. Google 로그인은 OAuth가 준비됐다는 말이 있을 때까지 제안하지 않는다. 실기기 테스트도 후순위다(2026-10-03).
