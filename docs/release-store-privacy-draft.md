# 스토어 개인정보 신고 초안

작성: 2026-10-11 · 상태: **답안 확정(2026-10-11 공식 정의 대조, 사용자 승인)** · 근거: PRD 8절, 출시 준비 결정, `node_modules`의 `PrivacyInfo.xcprivacy`

스토어에 낼 때 채우는 세 가지 — iOS Privacy Manifest, App Store 개인정보 라벨, Google Play 데이터 보안·연령 등급 — 의 답안 초안이다. **결제(RevenueCat)·광고(AdMob)를 붙이기 전 기준**이고, 붙인 뒤 늘어나는 항목은 각 절 끝에 따로 적었다. 2절 끝의 결제와 광고 표는 2026-10-28에 더했고 사용자 확인 전이다.

## 1. iOS Privacy Manifest (`app.json` `ios.privacyManifests`)

라이브러리가 낸 선언을 모은 것(2026-10-11, Expo 57.0.24 / RN 0.86.3).

| API 종류 | 이유 코드 | 누가 쓰나 |
| --- | --- | --- |
| UserDefaults | `CA92.1` | react-native, expo-constants, expo-system-ui |
| UserDefaults | `1C8F.1` (같은 App Group) | **expo-widgets** `WidgetsStorage` — 앱과 위젯이 App Group으로 주고받는다. expo-widgets는 자체 선언 파일이 없다 |
| 파일 시각 | `C617.1`, `0A2A.1`, `3B52.1` | react-native, Folly, boost, glog, expo-file-system |
| 시스템 부팅 시각 | `35F9.1` | react-native(timing), boost |
| 디스크 공간 | `E174.1`, `85F4.1` | expo-file-system |

```json
"privacyManifests": {
  "NSPrivacyTracking": false,
  "NSPrivacyAccessedAPITypes": [
    { "NSPrivacyAccessedAPIType": "NSPrivacyAccessedAPICategoryUserDefaults", "NSPrivacyAccessedAPITypeReasons": ["CA92.1", "1C8F.1"] },
    { "NSPrivacyAccessedAPIType": "NSPrivacyAccessedAPICategoryFileTimestamp", "NSPrivacyAccessedAPITypeReasons": ["C617.1", "0A2A.1", "3B52.1"] },
    { "NSPrivacyAccessedAPIType": "NSPrivacyAccessedAPICategorySystemBootTime", "NSPrivacyAccessedAPITypeReasons": ["35F9.1"] },
    { "NSPrivacyAccessedAPIType": "NSPrivacyAccessedAPICategoryDiskSpace", "NSPrivacyAccessedAPITypeReasons": ["E174.1", "85F4.1"] }
  ]
}
```

**넣은 방법 (2026-10-12)** — 위 값이 `app.json` `ios.privacyManifests`에 있다. Expo와 RN Pods 모으기는 **앱 타깃에만** 넣고 위젯 확장(App Extension)에는 넣지 않는다(RN `privacy_manifest_utils.rb`가 application 타깃만 고른다). 위젯도 RN·expo-widgets(App Group UserDefaults)를 링크하므로 로컬 플러그인 `plugins/widget-goal`이 같은 선언을 `ExpoWidgetsTarget/PrivacyInfo.xcprivacy`로 써서 위젯 리소스에 넣는다. 시뮬레이터 Debug 빌드에서 `app.app/PrivacyInfo.xcprivacy`와 `app.app/PlugIns/ExpoWidgetsTarget.appex/PrivacyInfo.xcprivacy` 둘 다 들어간 것을 확인했다.

**확인 못 한 것**

- Xcode Archive의 「Generate Privacy Report」(서명이 필요해 첫 TestFlight 빌드 때). 업로드가 ITMS-91053 없이 통과하는지.
- `NSPrivacyCollectedDataTypes`(수집 데이터)는 넣지 않았다. Expo 57 문서는 다루지 않는다. App Store 라벨(아래 2절)은 App Store Connect에서 따로 답한다.

## 2. App Store 개인정보 라벨 (App Privacy)

- **추적:** 하지 않음.
- **로그인하지 않은 사용자:** 기록이 기기 밖으로 나가지 않으므로 「수집」이 아니다. (1.0 기준. 1.1.0은 아래 「1.1.0 이벤트 기록과 오류 보고」 표가 대신한다.)
- **로그인한 사용자** (백업용, 모두 「사용자와 연결됨」, 목적은 「앱 기능」):

| 데이터 유형 | 무엇 |
| --- | --- |
| 연락처 정보 › 이메일 주소 | 계정 이메일(Apple 가리기면 중계 주소, 카카오는 받지 않음) |
| 연락처 정보 › 이름 | Google로 연결하면 Google이 넘기는 이름(인증 서버가 계정 정보로 저장, 앱은 쓰지 않음). 실제 저장 여부는 Google 로그인 뒤 `auth.identities`에서 확인 |
| 식별자 › 사용자 ID | 계정 식별자 |
| 식별자 › 기기 ID | 앱 설치 때 만든 무작위 값. 동기화할 때 어느 기기에서 바뀐 기록인지 구분하려고 보낸다(`src/sync/push.ts`, 처리방침 2절) |
| 사용자 콘텐츠 › 사진 또는 동영상 | 기록에 붙인 사진(줄인 것) |
| 사용자 콘텐츠 › 기타 사용자 콘텐츠 | 목표·스티커·메모. 1.1.0 함께 목표: 목표 이름, 함께 목표에서 쓰는 내 이름(10자), 고른 스티커, 붙인 칸과 시각, 신고 내용, 차단 목록(아래 「1.1.0 함께 목표」) |

- 진단(충돌 기록)·사용 데이터: 1.0에는 수집하는 SDK가 없다. 1.1.0은 아래 PostHog와 Sentry 표.

**결제와 광고를 붙인 뒤 더할 것 (2026-10-28 초안, 사용자 확인 전)**

근거는 Apple 「App privacy details」 원문("You need to identify all of the data you or your third-party partners collect"), 두 SDK가 스스로 밝힌 선언(`ios/Pods/Google-Mobile-Ads-SDK/.../GoogleMobileAds.framework/PrivacyInfo.xcprivacy` 13.6.0, `ios/Pods/RevenueCat/Sources/PrivacyInfo.xcprivacy`), Google 「App Store data disclosure」(2026-10-27 갱신본)이다. 광고 SDK가 모으는 것은 로그인과 상관없이 모든 사용자에게 해당한다. Apple의 선택 공개 예외는 「제3자 광고에 쓰지 않을 것」이 조건이라 광고 항목에는 쓸 수 없다.

| 데이터 유형 | 누가 | 목적 | 사용자와 연결 | 추적 |
| --- | --- | --- | --- | --- |
| 구매 › 구매 내역 | RevenueCat | 앱 기능 | 예 (로그인하면 계정 식별자로 `Purchases.logIn`, `src/purchases/revenueCat.ts:34`) | 아니요 |
| 위치 › 대략적 위치 | AdMob (IP로 추정) | 제3자 광고, 개발자 광고, 분석 | 예 | 아니요 |
| 식별자 › 기기 ID | AdMob | 제3자 광고, 분석 | 예 | **아니요 (추천안, 아래)** |
| 사용 데이터 › 제품 상호작용 | AdMob | 제3자 광고, 개발자 광고, 분석 | 예 | 아니요 |
| 사용 데이터 › 광고 데이터 | AdMob | 제3자 광고, 개발자 광고, 분석 | 예 | 아니요 |
| 진단 › 충돌 데이터 | AdMob | 분석 | 아니요 | 아니요 |
| 진단 › 성능 데이터 | AdMob | 제3자 광고, 개발자 광고, 분석 | 아니요 | 아니요 |
| 진단 › 기타 진단 데이터 | AdMob | 제3자 광고, 개발자 광고, 분석 | 아니요 | 아니요 |

- 「연결」과 「추적」 칸은 Google SDK 선언을 따랐다. Google 웹 안내는 이 두 칸을 나누어 적지 않는다.
- **기기 ID의 추적 칸은 사용자 결정이 필요하다.** SDK 선언은 기기 ID를 「추적에 사용」으로 적는다. 그런데 앱은 ATT를 묻지 않으므로 광고 식별자가 0이고(Apple 원문 "the device's advertising identifier value will be all zeros"), Google도 ATT 동의가 없으면 "the Google Mobile Ads SDK will not send the IDFA"라고 한다. 추천안은 실제 동작대로 「아니요」로 두고 앱 전체 「추적: 하지 않음」을 유지하는 것이다. SDK 선언 그대로 「예」로 적으면 스토어에 「사용자를 추적하는 데 사용되는 데이터」가 보이고 ATT 없이 추적한다고 읽힐 수 있다.
- 맞춤 광고로 바꾸면(RELEASE-DECISIONS 2026-10-05 「광고」) 기기 ID와 광고 데이터의 추적 칸을 다시 본다.

**1.1.0 이벤트 기록(PostHog)과 오류 보고(Sentry)를 넣은 뒤 더할 것 (2026-10-31 초안, 사용자 확인 전)**

이 표가 적용되면 위쪽의 「로그인하지 않은 사용자는 수집이 아니다」와 「진단과 사용 데이터는 수집하는 SDK가 없다」는 더 맞지 않으니 함께 고친다. 두 도구 모두 로그인과 상관없이 설치 ID로 보내고, 로그인하면 계정 식별자를 붙인다. PostHog는 스티커를 붙인 뒤 나오는 동의 시트에서 동의한 경우에만 보내고 처음에는 꺼져 있다. Sentry는 처음에 켜져 있고 설정에서 끈다(2026-11-01 결정). App Store 라벨은 일부 사용자에게서만 수집해도 수집으로 답하므로 아래 표는 그대로 답한다. 근거는 `src/analytics/`이고 이벤트 목록은 PRD 8.2다.

| 데이터 유형 | 누가 | 무엇 | 목적 | 사용자와 연결 | 추적 |
| --- | --- | --- | --- | --- | --- |
| 사용 데이터 › 제품 상호작용 | PostHog | 화면 이동과 앱 안 동작(PRD 8.2) | 분석 | 예 | 아니요 |
| 식별자 › 기기 ID | PostHog, Sentry | 앱 설치 때 만든 무작위 값(광고 ID 아님) | 분석, 앱 기능 | 예 | 아니요 |
| 식별자 › 사용자 ID | PostHog, Sentry | 로그인한 계정 식별자 | 분석, 앱 기능 | 예 | 아니요 |
| 진단 › 충돌 데이터 | Sentry | 앱이 멈춘 기록 | 앱 기능 | 예 | 아니요 |
| 진단 › 기타 진단 데이터 | Sentry | 화면 오류 내용, 기기 모델, OS, 앱 버전 | 앱 기능 | 예 | 아니요 |

- 광고 ID와 엮지 않고 다른 회사 데이터와 합치지 않으므로 「추적: 하지 않음」은 그대로다.
- 성능 측정은 켜지 않았다(`tracesSampleRate` 없음). 켜면 진단 › 성능 데이터가 늘어난다.
- 앱 `PrivacyInfo.xcprivacy`의 `NSPrivacyCollectedDataTypes`는 빈 배열이고 SDK가 채워 주지 않는다. 라벨은 App Store Connect에서 직접 답한다.

**1.1.0 함께 목표를 넣은 뒤 (2026-11-06 초안, 사용자 확인 전)**

함께 목표는 로그인해야 쓴다. 그래서 새 데이터 유형은 없고 위 「로그인한 사용자」 표의 「사용자 콘텐츠 › 기타 사용자 콘텐츠」 설명이 늘어난다(위 표에 더함). 목적은 「앱 기능」, 사용자와 연결됨, 추적 아님.

- 함께하는 사람에게 보이는 것: 목표 이름, 내 이름, 내 스티커, 붙인 칸. 초대 링크를 가진 사람은 로그인하지 않아도 목표 이름, 판 종류와 칸 수, 만든 사람 이름, 인원, 쓰는 스티커를 본다(앱과 웹 초대 페이지). App Store 라벨은 「누가 보는가」를 묻지 않으므로 라벨 항목은 늘지 않고, 처리방침 2판에 적는다.
- 신고 내용과 차단 목록은 운영자가 신고를 처리하고 차단을 지키려고 서버에 둔다. 같은 「기타 사용자 콘텐츠」, 목적 「앱 기능」.
- 초대 코드 맞히기를 막으려고 없는 코드를 넣은 접속 주소(IP)를 1시간 남긴다(`20261106000001`). 위치를 추정하지 않고 광고나 분석에 쓰지 않으므로 라벨의 「위치」로 적지 않는다. 처리방침의 서버 운영 기록 목적에 「부정 이용 방지」를 더한다.

**1.1.0 함께 목표 (2026-11-06 초안, 사용자 확인 전):** 「기타 사용자 생성 콘텐츠」에 함께 목표 이름, 함께 목표에서 쓰는 이름, 스티커, 붙인 칸, 신고 내용, 차단 목록을 더한다. 목적 앱 기능, 로그인할 때만. 함께하는 사람끼리 보이는 것은 앱 기능이라 「공유(제3자 전달)」로 적지 않는다(Google 정의: 다른 사용자에게 보이게 하는 것이 앱의 기능이면 공유가 아니다. 제출할 때 Play Console 설명을 다시 본다).

**1.1.0 이벤트 기록과 오류 보고를 넣은 뒤 (2026-10-31 초안, 사용자 확인 전):** 위 표의 「로그인할 때만」은 아래 항목에 해당하지 않는다. 두 회사는 처리를 맡은 곳이라 공유로 적지 않는다.

| 데이터 | 목적 | 필수/선택 |
| --- | --- | --- |
| 앱 활동 › 앱 상호작용 (PostHog) | 분석 | 선택 (스티커를 붙인 뒤 동의 시트, 설정에서 끈다) |
| 앱 정보 및 성능 › 비정상 종료 로그, 진단 (Sentry) | 앱 기능, 분석 | 선택 (처음에 켜져 있고 설정 「오류 보고 보내기」로 끈다) |
| 기기 또는 기타 ID (설치 ID) | 분석, 앱 기능 | 선택 (설정의 두 칸을 모두 끄면 보내지 않는다) |
| 개인 정보 › 사용자 ID (로그인한 경우) | 분석, 앱 기능 | 선택 (로그인하지 않아도 쓴다) |

삭제 요청 칸의 「예」는 이 데이터까지 지울 수 있어야 맞다. PostHog와 Sentry에는 앱 안 계정 삭제가 자동으로 닿지 않는다. 처리방침의 문의 메일로 요청을 받아 수동으로 지운다(2026-11-01 결정).

## 4. 연령 등급

**1.1.0 답안 (2026-11-06 초안, 사용자 확인 전).** 함께 목표가 들어가 1.0 근거(공유와 소통 기능 없음)가 더 맞지 않는다.

- 예상 등급: App Store는 사용자 콘텐츠가 「예」여도 신고와 차단이 있으면 4+로 남을 수 있지만, 2025년 새 설문에서 등급이 오르는지는 **확인 못 함**. 제출할 때 설문 결과 화면의 등급을 그대로 받아 이 표에 적는다. Google Play는 「사용자 간 상호작용」 표시가 붙고 등급은 IARC 결과를 따른다.

## 공식 정의와 대조한 결과 (2026-10-11)

사용자가 직접 판단하기 어렵다고 해서, 처음에 「정할 것」으로 남긴 세 가지를 스토어 공식 문서와 대조해 정했다. 법률 자문은 아니다.

1. **「로그인하지 않으면 수집 아님」 — 맞다.** Apple은 「기기 밖으로 보내 요청 처리에 필요한 시간보다 오래 읽을 수 있게 두는 것」을 수집으로 본다. Google도 「기기 안에서만 처리하고 밖으로 보내지 않는 데이터는 적지 않아도 된다」고 한다.
2. **「서버 위탁은 공유 아님」 — 맞다.** Google은 개발자 대신 데이터를 처리하는 서비스 제공업체로 보내는 것을 공유의 예외로 둔다. Apple 라벨에는 「공유」 칸이 따로 없고, 우리와 서버 업체가 수집하는 것을 모두 적으면 된다(위 표).
3. **계정 삭제 웹 경로 — 이미 있다.** Google 요건은 「열리고, 삭제 요청 방법이 잘 보이고, 앱이나 개발자 이름을 적을 것」이고 메일 접수도 인정한다. 정책 사이트의 `/delete-account/`가 모두 갖췄다.
4. **Privacy Manifest — 첫 TestFlight 업로드 전에 넣어야 한다.** 이유를 밝혀야 하는 API를 쓰는데 선언이 없으면 업로드 단계에서 ITMS-91053으로 막힌다. 위젯 같은 확장도 자기 선언이 필요하다는 안내가 있어, 넣고 빌드해 위젯 쪽에 들어가는지 확인한다.
5. **빠졌던 항목 — 기기 ID.** 처리방침 2절과 동기화 코드대로 설치 때 만든 무작위 값을 서버에 보내므로 두 스토어 모두 적는다(위 표에 더함).
