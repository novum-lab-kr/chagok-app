# 1.1.0 출시 순서

1.0.0 심사 결과에 맞춰 1.1.0을 언제 어떻게 내보낼지 정한 문서다. 2026-11-01 기준으로 썼고, 지금 상태 칸은 일을 진행하면서 고친다.

## 지금 상태

- **1.0.0은 빌드 7(`538f7eb`, production)로 심사에 냈다.** 지금 `origin/main`이 이 커밋이다. 빌드 번호는 2026-11-01 EAS 기록에서 확인한 값이다.
- **1.0.0 심사 결과는 확인 못 함.** 아래 표에서 지금 줄은 「심사 중」으로 잡았다. 결과를 확인하면 해당 줄로 옮긴다.
- 1.1.0 작업은 `release/1.1.0`에 모은다(`app.json` `version`은 이미 `1.1.0`).
- **버전 이름을 1.0.1에서 1.1.0으로 바꿨다(2026-11-04 사용자 결정).** 구독, 새 스티커 묶음, 다국어, 이벤트 기록까지 들어가 작은 수정판이 아니어서다. 브랜치도 `release/1.0.1`에서 `release/1.1.0`으로 옮겼다. 시험 브랜치 `test/1.0.1-integration`과 지난 PR 제목은 옛 이름 그대로다. 미뤄 둔 일은 1.1.1로 부른다. App Store Connect에 1.0.1 버전 페이지를 만들었다면 번호를 1.1.0으로 고친다(사용자).
- `v1.0.0` 태그가 `538f7eb`에 붙어 있다(원격에도 있음, 2026-11-04 확인). 1.0.0 긴급 수정은 이 태그에서 시작한다.

## 핵심 원칙

**운영 DB는 1.1.0 main 머지 때가 아니라 1.1.0 제출 직전에 바꾼다.** 심사와 승인 직후 사용은 곧바로 운영 서버를 쓴다. 제출 전에 서버가 준비돼 있으면 승인 순간에 따로 할 일이 없다.

**호환 시험을 통과하기 전에는 운영 DB에 넣지 않는다.** 2026-11-01 개발 서버 시험은 통과했다(아래 「호환 시험」).

### 처리방침 판

- 게시 시점은 아직 결정되지 않았다. 이벤트 기록 작업의 질문과 묶여 있다.
- 1.0.0 출시 전에 게시하면 1판을 고친다(AGENTS.md 「서버와 약관 규칙」).
- 출시 뒤에 게시하면 [출시 전 최종 점검](RELEASE-CHECKLIST.md) 6절대로 새 판을 내고 `versions.json`에 항목을 더한다.
- **점검 목록과 코드가 다른 곳:** 점검 목록은 「앱의 동의 판 번호를 올린다」고 적었지만, `release/1.1.0` 코드에서 고정된 판 번호를 찾지 못했다. 앱은 동의할 때 `versions.json`에서 시행 중인 판을 읽어 기록하고(`src/policy/manifest.ts`, `app/account/connect.tsx`), 새 판 안내도 그 파일로 정한다(`src/policy/versions.ts` `upcomingChange`). 새 판을 낼 때 앱 코드를 고칠 일이 있는지 그때 다시 본다.
- 운영 처리방침 1절의 「앱에는 이용 분석 도구가 없습니다」는 이벤트 기록이 든 앱이 나가기 전에 반드시 고친다.

### 스토어 상품과 결제 (제출 전, 2026-11-04 정리)

1.0.0 때 RevenueCat에 App Store 앱과 상품 5개(묶음 4개, 광고 제거)를 붙였다([출시 준비 결정](RELEASE-DECISIONS.md) 2026-10-26). 1.1.0은 아래 5개를 더한다. 상품 ID는 지운 뒤에도 다시 못 쓰니 한 글자씩 맞춰 본다(`src/purchases/revenueCatStore.ts`).

| 종류 | 상품 ID | 가격 | RevenueCat 권한 |
| --- | --- | --- | --- |
| 비소모성 | `com.novumlab.chagok.pack.christmas_normal` (크리스마스) | 2,200원 | `pack_christmas_normal` |
| 비소모성 | `com.novumlab.chagok.pack.study_normal` (공부와 일) | 2,200원 | `pack_study_normal` |

1. **App Store Connect:** 구독 그룹 하나를 만들고 월과 연 구독을 그 안에 둔다(둘을 동시에 결제하지 않게). 무료 체험과 할인 없음. 판매 지역은 대한민국만(앱과 같게). 상품마다 한국어 표시 이름과 설명, 심사용 스크린샷(그 상품을 사는 화면)을 넣는다. 4,900원과 24,900원이 원화 가격표에 있는지는 **확인 못 함.** 등록할 때 본다.
2. **처음 내는 구독은 앱 버전과 함께 심사받는다.** 1.1.0 버전 페이지의 「앱 내 구입 및 구독」에 새 상품 5개를 모두 골라 넣고 제출한다.
3. **RevenueCat:** 새 상품 5개를 가져와 위 표의 권한에 붙인다. 앱은 오퍼링을 쓰지 않고 상품 ID로 직접 부른다.
4. **약관과 메타데이터:** 자동 갱신 구독은 앱 안과 스토어에 이용약관과 처리방침 링크가 있어야 한다(Apple 개발자 계약 Schedule 2 제3.8(b)). 구독 조항은 이용약관 2판(시행 2026-12-04, novum-web PR #63)에 넣었다. 2판을 게시한 뒤 스토어 설명 끝이나 EULA 칸에 이용약관 주소를 둔다.
5. **확인:** TestFlight 빌드에서 샌드박스 계정으로 월 구독, 해지 예약, 끝남, 구매 복원을 본다.

## 운영 DB 반영

### 이번 변경

파일은 `supabase/migrations/20261030000001_goal_sort_order.sql`이다. `feature/goal-manual-order`에 커밋돼 있고 `test/1.0.1-integration`에 합쳤다. `release/1.1.0`과 main에는 아직 없다.

| 항목 | 내용 |
| --- | --- |
| 바꾸는 것 | `goals.sort_order` 칸 추가, `private.apply_upsert`와 `public.pull_changes` 교체 |
| 1.0.0이 올릴 때 | `sort_order` 없이 올려도 저장된 값을 지우지 않는다(`coalesce`) |
| 1.0.0이 받을 때 | 응답에 새 키가 늘어난다. 1.0.0은 칸을 골라 저장해서 새 키를 무시한다(확인함) |
| **1.0.0 동작이 바뀌는 곳** | 목표 올리기 조건이 `<=`에서 「시각이 같으면 지워지지 않은 행만」으로 바뀐다. 서버에서 지운 목표를 1.0.0이 같은 수정 시각으로 다시 올리면, 지금은 되살아나지만 적용 뒤에는 되살아나지 않는다 |
| 1.1.0이 먼저 나가면 | 파일 주석 기준으로 순서 값이 서버에 남지 않고, 지운 목표가 되살아날 수 있다. 그래서 제출 전 반영이 필수다 |

### 호환 시험

개발 서버에서 한다. 통과 전에는 운영에 넣지 않는다. 2026-11-01 결과:

| 항목 | 결과 |
| --- | --- |
| `npm run test:server`(목표 순서 코드) | 47개 모두 통과 |
| 1.0.0 소스(`538f7eb`)의 서버 시험 | 37개 통과, 4개 실패. 4개 모두 응답을 글자 그대로 비교하는 시험에 `sort_order: null`이 늘어난 차이뿐이다. 기기와 서버를 왕복하는 동기화, 복원 시험은 통과했다 |
| 새 키 때문에 1.0.0이 깨지는지 | 깨지지 않는다. 복원이 칸을 골라 저장한다 |
| 1.0.0이 순서 없이 올릴 때 | 저장된 순서가 남는다(실제 서버 시험, 옛 앱 형태의 행으로) |
| 지운 목표를 같은 수정 시각으로 다시 올리는 경로 | 1.0.0에 하나 있다. 아래 참고 |

**같은 시각으로 다시 올리는 경로:** `app/account/connect.tsx`의 첫 백업(`enqueueAll`)이다. 서버에 살아 있는 목표가 없고 기기에 기록이 있는 계정이 다시 연결할 때만 탄다. 적용 뒤에는 다른 기기에서 지운 목표가 이 경로로 서버에 되살아나지 않는다. 기기에는 남고, 그 목표를 고치거나 스티커를 붙이면 시각이 바뀌어 다시 올라간다. 드문 경로이고 데이터가 사라지지 않아 그대로 간다(2026-11-01 에이전트 판단).

**시험하지 않은 것:** 실제 1.0.0 기기와 1.1.0 기기를 번갈아 쓰는 동기화. 운영 반영 뒤 1.0.0 빌드로 확인하는 6번에서 본다.

### 반영 절차

정본은 `docs/post-launch-db-rules` 브랜치에 있는 [DEV-SETUP](DEV-SETUP.md) 「운영 DB 바꾸기」 절의 「출시 뒤」 초안이다. **이 초안은 아직 커밋 전이라 지금 DEV-SETUP에는 그 절이 없다.** 초안이 합쳐지면 그 절이 먼저고, 여기 요약은 순서만 적는다.

1. **비교:** 운영 `supabase_migrations.schema_migrations`의 `statements`를 main의 같은 버전 파일과 문장 단위로 비교한다. 이미 있는 버전에 차이가 있으면 멈춘다.
2. **백업:** 운영 서버에서 `pg_dump`로 덤프를 만든다.
3. **미리 보기:** 터널을 열고 `supabase db push --db-url ... --dry-run`으로 들어갈 파일이 새 파일 하나인지 본다.
4. **올리기:** 같은 명령을 `--dry-run` 없이 돌린다.
5. **함수:** 바뀐 폴더만 올린다. 목표 순서 작업에는 `supabase/functions` 변경이 없다. 합친 뒤 다시 확인한다.
6. **확인:** `goals.sort_order`와 바뀐 함수를 보고, 1.0.0 빌드로 동작을 확인한다.

초안의 터널 닫기는 `pkill`을 쓰지만, 여기서는 쓰지 않고 터널의 pid를 확인해 그 pid만 끈다.

### 되돌리기

- 호환 시험을 통과했다면 1.1.0이 반려돼도 되돌리지 않는다.
- 문제가 나오면 되돌리는 새 마이그레이션을 먼저 쓴다.
- 덤프 복원([운영 서버 복구](DEV-SETUP.md#운영-서버-복구))은 백업 뒤에 생긴 사용자 데이터가 사라지므로 마지막 수단이다.
